# 网关的 SQLite：写锁、丢不得的那两笔、和那条擦不掉的记号 —— 设计

日期：2026-11-21
状态：待定。
计划：`docs/superpowers/plans/2026-11-21-mmxcode-sqlite-write-lock.md`。

## 1. 原话

用户：「现在我们账号的状态怎么会出现：the token was written down but it was
not made durable: a power cut could lose it: flush the database: it is busy
这个错误呢？」

后来用户说：「你主要去查我们网关的sqlite的问题」。

## 2. 那条记号是哪里来的

**它是旧的版本写下的，现在的版本写不出来，也擦不掉。**

旧的版本里，store 有两个今天已经不在的东西：

- `Store.Flush()` —— 跑 `PRAGMA wal_checkpoint(FULL)`，把预写日志里的东西
  搬回主库；搬不动的时候它说的是 `flush the database: it is busy`。
- `manager.tokenNotDurableReason` —— 「the token was written down but it was
  not made durable: a power cut could lose it」。

那两条拼在一起，就是账号上挂着的那句话。写它的是**续签成功、可是写下去的那
笔没有落盘**的账号。

**证据**（不是推的）：

- 现在的分支里没有那句话，也没有 `Flush`：
  `grep -rn "flush the database\|not made durable\|it is busy\|func (s \*Store) Flush" internal/ cmd/` 空。
- 全部历史里，`tokenNotDurableReason` 只在计划文档
  （`docs/superpowers/plans/2026-11-19-mmxcode-sqlite-tuning.md`）里出现过，
  一行 Go 也没有进过仓库 —— 那个版本是从没提交过的工作树里编出来的。
- 跑着的那个二进制（PID 33040，2026-11-20 20:32 编的）里，flush / durable /
  busy 这些字眼一个也没有。
- 库里的 46 个账号全是 `active`，而且**都有令牌行**（100 个账号一个不缺），
  令牌的到期时刻最晚是 2026-11-21 07:19:39。也就是说：那些令牌照样能用，
  那条记号说的事情已经不成立了。

**所以现在要修的不是「别再写那条记号」** —— 现在的版本已经不会写它了
**—— 而是「把它擦掉」。**

### 2.1 为什么擦不掉

`manager.clearTokenNote` 只认自己写的那一条前缀：

```go
if !strings.HasPrefix(a.LastError, tokenNotWrittenReason) {
	return
}
```

旧的记号说的是另一句话（前缀不同），所以这个 `HasPrefix` 永远不成立 ——
**没有任何一条代码路径能把它擦掉**。它会一直挂在那里，直到那个账号下次改
状态（改状态才会顺带把 `last_error` 清空）。

### 2.2 还有一处：库追上了，记号也不擦

`manager.saveToken` 开头有一道守卫：库里那份令牌不比手里那份旧，就不写。

```go
stored, err := m.Store.GetToken(ctx, accountID)
if err == nil && !stored.ExpiresAt.Before(store.AtMillisecond(tok.Expires)) {
	// The store already holds a token that is at least as new.
	return nil          // ← 这里直接返回，没有擦记号
}
```

这道守卫是对的（旧的令牌不该盖新的），但**它顺手把记号留下了**：库里那份既
然不比手里那份旧，那条「库里那份比手里那份旧」的话就**不成立了**，记号该擦。
写成功了才擦（`saveToken` 的最后一行 `m.clearTokenNote`）是对的，可是**跳过
写入的那条路没擦**。

## 3. 现在的账：写锁

SQLite 只有一个写锁。网关里所有的写都要它。量出来的东西（在一个临时模块里
用同一个驱动量的，跟库里用的是同一个 `modernc.org/sqlite v1.62.0`）：

| 量 | 数 |
|---|---|
| 提交一次的开销（`synchronous=normal`） | 64 µs |
| 提交一次的开销（`synchronous=full`） | 874 µs |
| `busy_timeout` 是不是真的等了 | 是：写被占住的时候等了 5.1 秒，然后报 `database is locked (5) (SQLITE_BUSY)` |
| `BeginTx` 会不会自己等 | 会：等了 2.7 秒，然后拿到了锁 |
| 一条连接上两个被堵住的写 | 一个 5 秒，一个 **7.8 秒**（排队） |
| 四条连接上八个并发事务 | 0 个失败 |

库里现在的形状：`mmxcode.db` 352,256 字节，预写日志 4,128,272 字节。**日志的
大小是稳的**（量了三次，一个数都没变），所以那不是漏，是陈旧的文件 —— 一
次 TRUNCATE 检查点（在一份拷贝上做的）回的是 `(0,0,0)`：没有等着搬的东西。
`wal_autocheckpoint` 是默认的 1000 页，日志正好卡在这个数附近。

## 4. 找到的洞

### 洞一：那条记号擦不掉（§2.1、§2.2）

上面两处。

### 洞二：事务里写的令牌没有落盘

规格里定死了一条：**丢不得的那两笔走一条会 fsync 的连接**（续签后的令牌、
清掉的「用完了」标记）。store 里那条连接是 `Store.durable`。

可是令牌有两个写法：

- `Store.SaveToken` —— 走 `s.durable`（fsync）。✓
- `sqlTx.SaveToken` —— 走事务，也就是**平时那条连接**（`synchronous=normal`，
  不 fsync）。✗

`sqlTx.SaveToken` 是**签入**和**导入**用的（`Store.SignIn` 和
`internal/provision/chain.go`）。这两个地方写的都是令牌，而「库里的令牌比手里
的旧」是最坏的那种丢：库里留着的是一个**已经被站点用掉**的 refresh token，
下一次续签站点会拒，账号就被记成签入失效。

导入那条路更明显：清单里的号**已经在库里**的时候，导入带去的是一枚新的
refresh token。这一笔要是没落盘，库里留着的就是旧的、已经用掉的那一枚。

### 洞三：库说忙的时候，没人再试一次

- **store 里没有一处认「忙」**。`busy_timeout(5000)` 等满了，写的那个语句就
  失败了，失败就是失败。
- 整个仓库里唯一认忙的地方是 `internal/provision/chain.go` 的
  `busyLibrary` —— **靠字眼认**：

  ```go
  s := strings.ToLower(err.Error())
  return strings.Contains(s, "locked") || strings.Contains(s, "busy")
  ```

  别的毛病（消息里有个 "busy"）也会被认成忙，反过来也一样。

- 驱动其实**给了正确的办法**：`modernc.org/sqlite.Error` 有 `Code() int`，
  5 是 `SQLITE_BUSY`，6 是 `SQLITE_LOCKED`。按结果码认，才是认「忙」。

- 驱动还有一件更好的事：**它自己的忙处理器看调用者的 context**。context 到
  了，它就放弃等待（`busy.go` 的 `busyHandler`）。所以**等待的长短是可以由
  我们自己定的**，不必是连接上的那个 `busy_timeout`。

### 洞四：一条连接排成一队

`durableConns = 1`：那条 fsync 的连接只有一条。

写锁只有一把，所以两条连接也还是一把锁 —— 但**排队的样子不一样**：

- 一条连接的时候，第二个写**在 Go 这边排队**（等一条空连接），等第一条放弃
  了（5 秒）它才拿到连接，然后**再等 5 秒** —— 量出来是 5 秒和 7.8 秒。
- 两条连接的时候，两个写**一起在 SQLite 的忙处理器里等**，一起在 5 秒左右
  结束。

所以那一条连接不只是慢，还是**把等待翻倍**。

## 5. 改什么

### 5.1 记号：库追上了就擦

`manager.saveToken` 那道守卫**不写的时候也擦**：

```go
if err == nil && !stored.ExpiresAt.Before(store.AtMillisecond(tok.Expires)) {
	// 库里那份不比手里那份旧 —— 那条「库里那份比手里那份旧」就不成立了。
	m.clearTokenNote(ctx, accountID)
	return nil
}
```

`clearTokenNote` 认**两条**前缀：现在写的那条，和旧版本写的那条。

### 5.2 记号：旧版本写的，开机时擦掉

旧的记号说的是一句今天已经不存在的话（「写下去了，可是没有落盘」—— 现在
那笔走 fsync 的连接，它落盘了）。所以那条记号**已经不成立了**，该擦。

- store 给一个原语：`ClearAccountNotes(ctx, prefix)` —— 把所有以这个前缀开
  头的记号擦掉。
- manager 认得旧的那句话（**词汇是 manager 的**，store 不该知道 manager 写什
  么），所以 manager 来擦：`ClearRetiredNotes(ctx)`。
- 开机的时候擦一次：`cmd/mmxcode/root.go` 建好 manager 之后调一下。擦不掉
  就说一声，不挡着网关起（那是一次收拾，不是网关的命）。

### 5.3 事务里的令牌也落盘

`store.tx` 走 `s.durable` —— 事务的提交会 fsync，所以**事务里写的令牌是落盘
的**，而且**账号行和令牌行是一起落盘的**（读者不会看见一行没有令牌的账号）。

代价：签入和导入的提交从 64 µs 变成 874 µs。这两件事很少发生（一次签入、
一次导入的一千个号里每个号一次 —— 一千次 fsync 也就是一秒）。

### 5.4 库说忙的时候，再试一次

- store 有 `Busy(err) bool`：按**结果码**认忙（5 = `SQLITE_BUSY`，6 =
  `SQLITE_LOCKED`），不靠字眼。`internal/provision` 的 `busyLibrary` 换成用它
  （那个函数整个删掉）。
- **丢不得的那两笔**（`SaveToken`、`ClearExhausted`）和**事务**：库说忙就再
  试一次。
  - **一遍等一秒**：那是丢不得的那两笔走的那条连接上的 `busy_timeout`
    （平时那些写还是五秒 —— 它们丢了都能自己好起来，等得久一点没事）。
    那条连接等得**短**一点，是为了让「再来一遍」有意义：库的忙处理器越等
    越粗（一开始 1 毫秒，后来 100 毫秒），占着锁的那件事中间让出来的空当
    （导入的时候，一笔账一个事务）它就错过了 —— 再来一遍是新的忙处理器，
    它又从 1 毫秒开始等。
  - **一共五遍**，中间歇 50 毫秒。遍数是「总的工夫那个顶（5 秒）除以一遍
    的工夫（一秒）」，最多五遍。
  - 一共等 ≈ 5.2 秒 —— **跟从前的一遍 5 秒差不多**，可是有五回机会。
- 平时那些写（额度快照、会话、记号……）**不动**：它们丢了都能自己好起来，
  为它们把请求拖住不值。

**为什么不是「一遍等五秒，失败了再来一遍」**：那样一遍失败就是五秒，两遍就
是十秒 —— 请求的路上一分都不能慢。**为什么不是「等更短，多来几遍」**：等
得太短，锁占着的时候（一秒）还没放，就白等了几遍。

### 5.5 那条 fsync 的连接有两条

`durableConns` 从 1 改成 2：写锁还是一把，可是两个写**一起等**，不用一个等
另一个放弃（§4 洞四）。

## 6. 不做什么

| 不做 | 为什么 |
|---|---|
| 把 WAL 检查点搬回来 | 旧的 `Flush` 就是在做这件事，而它「搬不动」的时候说的话就是用户看到的那句。WAL 自己会检查点（日志大小是稳的，§3） |
| 把平时那条连接的 `busy_timeout` 从 5000 改掉 | 平时那些写靠它等；丢不得的那两笔走的是另一条连接，那条等一秒（§5.4） |
| 给所有写都加「再试一次」 | 平时那些写丢了都能自己好起来，为它们把请求拖住不值 |
| 把事务整个搬去 fsync 那条连接**之外**的办法 | 账号行和令牌行必须一起落盘（§5.3） |
| 动 `last_error` 以外的东西 | 这次只动那一条记号 |

## 7. 行为变了的地方

1. **库里那份令牌不比手里那份旧的时候，那条记号会被擦掉**（从前不擦）。
2. **开机的时候，旧的记号被擦掉**（46 个账号 —— 从前永远擦不掉）。
3. **事务里的令牌落盘了**（从前不落盘）。
4. **库说忙的时候，那两笔丢不得的写会再试**（从前等 5 秒然后失败；现在一共
   ≈ 5.2 秒，五回机会）。
5. **两个写一起被堵住的时候，一起在 5 秒左右结束**（从前是 5 秒和 7.8 秒）。

## 8. 怎么量

- **旧版本写的记号被擦掉**：一个只有那条记号的账号，开机之后那条记号没了。
  （拿真库的一份拷贝验过：46 条 → 0 条，100 个账号一个不少。）
- **库追上了，记号就没了**：写失败一次留下记号，之后库里那份令牌追上了，
  记号被擦掉。
- **事务里的令牌是落盘的**：那条 fsync 的连接关掉之后，事务就起不来 ——
  这就是「事务走的是那条连接」的证据（那条连接是会 fsync 的那条）。
- **库说忙的时候，那笔写还是写下去了**：另一个连接占着写锁，占着的工夫比
  一遍的等待长；锁放开之后，那笔写写进去了。
- **忙是按结果码认的**：一个消息里有 "busy" 两个字的错**不是**忙；一个
  `SQLITE_BUSY` 的错**是**忙。
- **两个写不排队**：那条 fsync 的连接有两条（从前一条）。

## 9. 风险

| 风险 | 怎么办 |
|---|---|
| 擦记号的时候把**真话**也擦了 | 只擦自己认得的那两条前缀；别的理由（续签失败但手里那份还好之类）说的是别的事，擦了就是把真话藏起来 |
| 事务改成 fsync 之后慢了 | 签入一次 874 µs；导入一千个号多一秒。那两件事很少发生 |
| 再试的工夫把请求拖住 | 一共 ≈ 5.2 秒，跟从前的一遍 5 秒差不多，可是有五回机会 |
| 擦旧记号的时候，别的进程正在写账号 | 那是一遍 `UPDATE ... WHERE last_error LIKE ?`，写锁只有一把，别的写等一下就是（等不到就还是等 —— 和从前一样） |
