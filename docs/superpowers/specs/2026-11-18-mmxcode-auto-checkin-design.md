## 1. 原话

> 「现在账号的签到并没有自动功能。规划一下吧」
>
> 「签到的号进不了池, 按照大陆的时间签到（00:00)，然后慢慢签到没有关系1000个号也就1000秒。花不了多久。」
>
> 「00:00 跑一趟 + 启动时补签（推荐）」

## 2. 签到这一半已经有了，差的是它跟池的那一头

签到早就有了，只是没接上：

| 在哪 | 是什么 |
|---|---|
| `internal/scheduler/scheduler.go:301-317` | 每天跑一趟，串行，**所有**号都签一遍 |
| `internal/manager/manager.go:1054` | 续 token → 调站点 → `SaveCheckin` 写库 |
| `internal/checkin/checkin.go` | 面板 + 领取，五个结果：claimed / done / ineligible / inactive / failed |
| `cmd/mmxcode/checkin.go` | 命令行手动签到 |
| `internal/webui/webui.go:650` | 页面上每个号的「立即签到」 |

差的是五件事：

| # | 差在哪 | 现在 | 要的 |
|---|---|---|---|
| 1 | **时刻** | `NextCheckin` 按**本机时区**算 09:00（`scheduler.go:80-89`） | 按**大陆时间**算 00:00 |
| 2 | **补签** | 没有：服务器 00:00 没开着，这一整天的签到就没了 | 启动时补上 |
| 3 | **签哪些号** | 所有号都签一遍（签过的也签，站点答 done，白花一次调用） | 只签今天还没签的 |
| 4 | **积分进池** | 池里那份数是进池那一刻的，签到给的积分池不知道 | 池里那份数要换 |
| 5 | **重试** | 失败的号当天不再签 | 不做（见 §8） |

## 3. 关键的那件事：池里那份数是进池那一刻的

池里一个号带两样东西：账号行，和它**进池那一刻**的剩余积分（`internal/pool/pool.go:37-48`）。

轮转就是拿这份数排序的（`internal/rotator/rotator.go:625-650`）：

1. 读到余额的排前面（没读到的不算零，它排在有数的号后面）；
2. 读到「0」的排到有数的号后面 —— 它接不了活了，挑它就是撞一次空；
3. 最久没用过的排前面；
4. 一样的话余额多的排前面。

所以签到完了以后，那个号在池里还是签到前的那份数：

- **签到前是 0 的号**：池里还是 0 → 排在所有有数的号后面 → 签到给的 7 天积分白瞎（它排在最后，别人先挑）；
- **根本不在池里的号**：更远一层 —— 补号的候选排序里没有签到这一项（`internal/store/pool.go:78-84`：对话绑着的号 → 从没读过的号 → 读得最早的号）。签到过的冷号落在「读得最早」那一档，得等前面那些号都轮完才轮得到它。

库里的真相一直都在：`checkins` 表记着今天谁签到、给了多少积分（`internal/store/schema.go:157-178`，`UNIQUE(account_id, day)`，`credit` 这一列）。**缺的不是记录，是池跟它的那条路。**

## 4. 三条路，选一条

### 做法 A：池问库（拉）—— 选这个

网关每一趟补号问库一次：**今天签到给了积分的那些号**。对池里的那些号，把池里那份数换成「不小于签到的积分」；不在池里的那些号，靠候选排序排到前面进去。

- 真相只有一处（库的 `checkins` 表）。命令行签的、页面上签的、调度器签的，池都看得见 ✓；
- 网关重启也不丢：库里还记着昨天签到给了多少 ✓；
- 代价：一趟一次小查询（要一个 `day` 上的索引）。

### 做法 B：签到告诉池（推）

`Mgr.Checkin` 签完立刻回调网关：「这个号拿到 N 积分」，网关当场把池里那份数换掉。

- 好处：立刻生效，不用等下一趟；不用查库。
- 坏处：管理器得认识网关的池（多一层耦合）；命令行的签到跑在另一个进程里，正在跑的网关看不见；网关停机时发生的签到，起来以后池里那份数还是旧的（要等填池时重新读一次额度才准）。

### 做法 C：池里那份数一律从库里刷新

池里每个号记着自己那份数是什么时候的，每趟跟库里比，库里的新就换。

- 好处：最彻底 —— 池里那份数永远不比库里旧，签到只是其中一个原因。
- 坏处：**签到的积分还是晚**。库里的「读数」是读额度那一趟写下的，而签到完的那一趟只读 `usage.refresh.batch`（6 个）号（`internal/scheduler/scheduler.go:127-148`），剩下 994 个靠「签到待补」那一档慢慢读（`internal/usage/round.go:104`）：1000 个号要 12 个/分钟 ≈ 83 分钟。**用户抱怨的正是这个**：签到的积分进池太晚。
- 而且它给每个条目都要加一个时间戳。

**选 A。** 它最省（不额外读上游）、最贴近「池只是缓存，库才是真相」这条线，而且签到的积分最迟 30 秒就进池。

## 5. 设计

### 5.1 什么时候签

- **每天一趟，按大陆时间 00:00**（`schedule.checkin_at`，默认从 `"09:00"` 改成 `"00:00"`）。
- **时区是站点的，不是机器的。** 站点按大陆时间算一天（`store.DayKey` 已经这么算，`internal/store/store.go:2315-2338`），签到必须落在站点的这一天里，所以触发时刻也按大陆时间算。
  - 现在 `NextCheckin` 用的是 `now.Location()`（本机时区）：一台 UTC 的机器上「00:00」是大陆时间 08:00，差 8 个钟头；一台东京的机器上「00:00」是大陆时间前一天 23:00 —— 签到落在站点的**前一天**，那天的积分拿不到（站点按自己的日子发）。
  - 改法：`NextCheckin` 按 `store.CheckinZone()` 算。站点在哪个时区是站点的事（站点按大陆时间算日子），不是用户的偏好，所以**不加配置项**。
- **抖动**：现在有 0~30 分钟的随机延迟（`scheduler.go:302`）。它是为了「好几个实例别在同一秒压站点」，而这里一个实例、号又是一个一个签的，抖动只是把开始往后推。改成配置项 `schedule.checkin_jitter`，默认 `"0"`。

### 5.2 签哪些号

- **只签今天还没签到的号。**「今天」= 站点的那一天（`store.DayKey`，大陆时间）。
- 凭据是 `checkins` 表里有没有那一行（`UNIQUE(account_id, day)`）。
- 这一条同时解决三件事：
  - 服务器 00:00 没开着 → **启动时补签**只补漏的 ✓；
  - 00:00 跑到一半崩了 → 下次启动接着补剩下的 ✓；
  - 页面上手动签过的号 → 不重复签（站点会答 done，白花一次调用）✓。
- 签过但结果是 ineligible / inactive / failed 的号，今天不再签：ineligible 是站点说今天不给签，inactive 是这个号不在签到的名单里，failed 是签不上（token 掉了，要的是重登不是重签）。这些号**明天那一趟自然会再被签到**（新的一天，谁都没有行）。

### 5.3 签到的积分怎么进池

**库里那份数** → **池里那份数**：

- 网关每一趟补号（`usage.refresh.scan_every`，默认 30 秒）问库一次今天签到给了积分的号。
- 对**池里**的那些号：把池里那份数换成「不小于签到的积分」：

  ```go
  if !e.Known || e.Remaining < credit {
      s.Pool.SetRemaining(accountID, credit, true)
  }
  ```

  - 为什么不是「加上」：池里那份数可能是签到**之后**读到的 —— 读额度那一趟会把签到的积分读进去（`internal/usage/round.go:104` 的「签到待补」就是为这件事排的）。那时候再加一遍就是说它有更多的额度，是多说。
  - 为什么不是「换成签到的积分」：签到前的余额可能还剩着（那是上一天留下的），换成签到的积分就把那部分丢了。取两者的**较大值**，两边都不会说错。
  - 池里那份数只是「这个号有没有额度」的**提示**（排序规则 1、2、4）。提示只要说「有」就够，确切是多少由读额度那一趟慢慢补上（它写回库，下一次进池时就是准的）。
- 对**不在池里**的那些号：靠**候选排序**排到前面 —— `PoolCandidates` 的排序加一条「今天签到过的排前面」，位置在「对话绑着的号」之后、「从没读过的号」之前。
  - 为什么在「从没读过的」之前：签到过的号一定刚拿到积分（7 天有效），而从没读过的号有没有额度是**不知道的** —— 填池那一趟要读它，读到 0 就白读一次（2~11 个上游请求）。
  - 排前面的号进池时读一次额度（`pool.read_on_admit`），池里那份数就是准的 ✓。
- **池满了**：签到的号排在前面，但满的池挤不进去。池不赶人 —— 池里绑着对话的号不能赶（规格不变量 3），额度用完的号自己会出池（规格 §4.4）。签到过的号在池外等着，池一转起来就轮到它。

### 5.4 配置

| 键 | 现在 | 变成 | 为什么 |
|---|---|---|---|
| `schedule.checkin_at` | `"09:00"`（本机时区） | `"00:00"`（**大陆时间**） | 用户要的 |
| `schedule.checkin_jitter` | 没有（写死 0~30 分） | `"0"` | 一个实例、串行签，抖动没必要；想摊开的人自己配 |

`schedule.checkin_jitter` 用 `OptionalDuration`（`config.Duration` 不许 0，这个键的 0 有确切的意思：不抖）。

`cmd/mmxcode/serve.go` 里那句校验的错话（「调度器会默默按 09:00 跑」）也要跟着改。

### 5.5 出错了怎么办

| 出什么错 | 怎么办 |
|---|---|
| 签到时网络错、token 掉了 | `Mgr.Checkin` 记 outcome=failed（或返回错误不写行）→ 今天不再签它（明天再来） |
| 池刷新问库失败 | 记日志，下一趟再来；这一趟池里那份数是旧的（不好也不坏） |
| 签到跑到一半服务器停了 | 没签到的号没有行 → 下次启动补签 ✓ |
| 网关重启 | 池用库里的数重新填（`SeedPool`），签到待补的号排在前面 ✓ |

### 5.6 卡上的余额

签到完的那一趟只读 6 个号（`usage.refresh.batch`），所以**卡上**的余额不是立刻就准的 —— 剩下的号由「签到待补」那一档慢慢读（1000 个号约 83 分钟）。

要让卡立刻准，就得在签到后给每个号再读一次额度（每个号 2~11 个上游请求，1000 个号是 2000~11000 个请求）。这是上游的账，本设计不付（§8）。

## 7. 怎么测

- **store**：`DayCheckins` 只给今天签到给了积分的号；`AccountsWithoutCheckin` 只给今天没签到的号（签过的、别的日期的都不给）；`PoolCandidates` 把今天签过的号排在从没读过的号前面。
- **gateway**：池里的号签到后，池里那份数不小于签到的积分；池里那份数本来就比它大的时候**不变**（不多说）；没读过的号（`Known=false`）签到后变成「读到余额」。
- **scheduler**：下一趟签到是**大陆时间**的下一个 00:00（在一台 UTC 的机器上算出来也是那个）；只签今天没签到的号；起进程就补签一趟。

## 8. 不做的事

- **不做签到失败的重试**。失败就是失败：token 掉了要的是重登（`batch.relogin` 那一趟管它），不是重签。
- **不做并发签到**。用户说了串行慢慢签（1000 个号 1000 秒）。
- **不签完立刻给每个号读额度**。卡上的余额晚一点准，是上游读额度的账（§5.6）。
- **不改池的容量、不动轮转的排序规则**。这一版只让签到的积分进池。
