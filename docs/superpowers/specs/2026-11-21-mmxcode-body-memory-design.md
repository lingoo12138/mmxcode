# 一个身体在飞的时候占多少 —— 设计

日期：2026-11-21
状态：待定。
计划：`docs/superpowers/plans/2026-11-21-mmxcode-body-memory.md`。

上一份：`docs/superpowers/specs/2026-11-21-mmxcode-body-lanes-design.md`
（那份把身体分了道：大的一个一个来，小的有字节池。那份算的是「在飞的身体
占多少字节」，但没算「读它的时候占多少」—— 这份是那个数。）

## 1. 原话

> 「嗯。 没错。我们就是要防止大请求过分占用内存，导致其他请求没法处理。」

道分好了，账也算出来了（144 MiB），但那是**账**。量出来的是另一个数。

## 2. 量出来的

2026-11-21，一个探针站在真的网关前面，打一个 63 MiB 的身体进去：

| | 堆峰值 | 这段时间里分配的 |
|---|---|---|
| 之前 | **378 MiB** | 409 MiB |
| 之后 | 63 MiB（就是身体本身） | 63.2 MiB |

378 MiB 是 63 MiB 的**六份**。一个 64 MiB 的上限，进来的是六份 —— 那六份
是哪六份，量出来了：

| 那一份 | 多少 | 为什么 |
|---|---|---|
| 身体本身 | 63 MiB | 躲不开的 |
| `io.ReadAll` 的翻倍 | ~127 MiB | ReadAll 一路翻倍着长大：16 MiB 的身体它要分配 32 MiB，翻倍的那一刻两份都在 |
| `firstUserOf` 的 RawMessage | 63 MiB | 抄下整段 raw，只为了知道「里面有没有文字」 |
| `firstUserOf` 解出来的文字 | 63 MiB | 抄下来的那份还要再解一遍 |
| 会话哈希的拼接 | 63 MiB | `system + "\x00" + firstUser` 拼出来是一份 |
| 会话哈希的 `[]byte(s)` | 63 MiB | 转成字节又是一份 |

还有一样量不出来但一样贵：身体被**读**了四遍（`modelOf`、`isStream`、
`systemOf`、`firstUserOf`，各一次 `json.Unmarshal`）—— 一个 63 MiB 的身体
读四遍要 1.5 秒的 CPU。

## 3. 改了什么

### 3.1 读身体：照着它说的那个数读一次

客户端说了多大（`Content-Length`）就照着那个数读，一次读完。翻倍没有了，
那 ~127 MiB 没有了。

不知道多大（分块传的）还是 `MaxBytesReader` 挡着 —— 那是唯一一种能超过
`Content-Length` 的。

### 3.2 身体里的东西：读一遍

四个 `json.Unmarshal` 合成一个：模型、流式、会话三样都从同一次读里拿。
一个 63 MiB 的身体读一遍要 0.4 秒（读四遍要 1.5 秒）。

### 3.3 文字：指着一段字节，不抄

`json.RawMessage` 抄下整段 raw —— 一张几十兆的图片就是几十兆的白抄，抄完
只是为了知道「这段里没有文字」。

改成指着身体里原来那一段（标准库给 `UnmarshalJSON` 的那段字节本来就是身
体里的一段，不是抄的）。图片的 base64 在别的字段里（`source`、
`image_url`），标准库看它不看就跳过去了 —— 一个字节也不抄。

于是：

- 一张 63 MiB 的图片：抄 0 字节。
- 一段 63 MiB 的对话：只有**第一条**用户消息的文字被留着（它要算会话
  哈希），别的消息一个字都不留。

有转义的时候（`\"`、`\n`）那不是原来那段字节了，那时候才抄一份 —— 那样
的身体不多见。

### 3.4 会话的哈希：分块写进去，不拼

`sha256(system + "\x00" + firstUser)` 拼起来是两份，转成字节又是一份。
改成一块一块写进哈希里：**哈希出来的东西一个字节都不差**（写进去的还是
同样的那些字节，同样的顺序），多的那点地方是固定的 32 KiB。

### 3.5 转换：指着身体，不抄

OpenAI 和 Codex 的身体要转成 Anthropic 的形状（`convert.ToAnthropic*`）。
转的时候也在抄：

| | 之前 | 之后 |
|---|---|---|
| OpenAI，63 MiB 的**文字** | 534 MiB | 410 MiB |
| OpenAI，63 MiB 的**图片** | 72 MiB | 6 MiB |
| Codex，63 MiB 的图片 | 336 MiB | 6 MiB |

（这几行是转换**自己**分配的，不算身体本身。）

抄的是这些：

- `chatMessage.Content` 是 `json.RawMessage` → 抄下整段内容。改成指着身体
  里那一段。
- Codex 那边每一项都 `mustMarshal` 重新写一遍再读一遍 → 直接读原来那一段。
- `strings.TrimSpace(string(raw))` → `bytes.TrimSpace(raw)`（抄一份只是为了
  看看是不是 `null`）。
- 输出那份 JSON 写进一个**开够了的**缓冲：标准库自己开的那块一路翻倍着长
  大（63 MiB 的输出要分配 126 MiB 的缓冲），开够了就只抄一遍。缓冲按留下
  来的文字算，不按身体算 —— 一张几十兆的图片在 OpenAI 那边是没有的
  （它被丢掉了），按身体算就是白开一块几十兆的缓冲。

## 4. 量完之后

| | 之前 | 之后 |
|---|---|---|
| 一个 63 MiB 的身体（Anthropic） | 378 MiB 堆峰值，409 MiB 分配 | **63 MiB**（就是身体本身） |
| 读身体的 CPU | 读四遍，1.5 秒 | 读一遍，0.4 秒 |
| 转换（OpenAI，图片） | 72 MiB | **6 MiB** |
| 转换（Codex，图片） | 336 MiB | **6 MiB** |

于是身体分两条道那份设计算的账**成了真的**：

| | 在飞的身体 | 算得出来吗 |
|---|---|---|
| Anthropic | 64（大）+ 80（小）= **144 MiB** | 算得出来，而且现在是真的 |
| OpenAI / Codex | 208 MiB（转换的那份拷贝是最坏的情况：整个身体都是文字的时候） | 算得出来 |

## 5. 不做什么

- **不改两条道**：那份设计不动。这份只管「一个身体进来的时候占多少」。
- **不改 `maxBodyBytes`**：还是 64 MiB。
- **不手写转换出来的 JSON**：标准库那一套（翻倍着长大的缓冲）是那份转换
  的账里最大的一块，但手写 JSON 是另一件事，风险也是另一件事 —— 转换出来
  的东西要跟上游对得上，错了就是静默的错。这份只把白抄的拿掉。
- **不改会话哈希的值**：哈希的还是同样那些字（转义之前的），所以存着的
  那些会话还认得出来。

## 6. 怎么量

1. **读身体不翻倍**：读一个 16 MiB 的身体，分配不许超过 20 MiB
   （`TestTheBodyIsReadIntoOneBuffer`）。
2. **图片不抄**：读一个带 16 MiB 图片的身体，分配不许超过 1 MiB
   （`TestTheImageIsNotCopied`）。
3. **对话不抄**：读一个带 16 MiB 消息的身体，分配不许超过 1 MiB
   （`TestTheWholeConversationIsNotCopied`）。
4. **哈希的是字，不是字节**：转义过的「one\ntwo」算出来的会话，跟直接写
   进去的「one\ntwo」是同一个（`TestTheSessionHashesTheWords`）。
5. **转换的账**：`internal/convert` 里的三个基准（`BenchmarkTheConversionOf*`）。
