# 大身体和小身体：两条道 —— 设计

日期：2026-11-21
状态：待定。
计划：`docs/superpowers/plans/2026-11-21-mmxcode-body-lanes.md`。

上一份：`docs/superpowers/specs/2026-11-21-mmxcode-request-body-limit-design.md`
（那份把闸门挪到了读身体之前、把上限抬到 64 MiB。这份接着那份：身体的大小
现在知道了，接下来是「知道多大之后怎么办」。）

## 1. 原话

同一件事，用户说了三个版本。

先是那把锁：

> 「我有个想法，如果我们知道哪个请求体大，我们可以加一个锁，把大的请求体的请求发送的到上游的瞬间解锁，可能会损失一些性能，但是可以保证内存资源不会被并发撑的太大」

然后是排序：

> 「你看看我的需求和你的设计对得上吗？比如检测到有大的请求体，我们就要做堵塞，先把大请求体解决，再恢复其他小的正常文本类的请求。」

我给的那个设计（**预算按大小排队 + 队头阻塞**）**对不上**。它是「大的先走、
小的让路」：大请求在等的时候，空着的预算故意不给小请求用，小请求排队等，超时
就是 429。排序对了，代价做反了 —— 用户要的是「大的不受小的拖累」，我做成了
「小的受大的拖累」。

最后是形状：

> 「替代方案也行，我们只同时处理一个大的请求，64mb，结合小的请求，总并发20的
> 情况下，19*4mib也就不到80MIB，能接受。」

**这就是要的形状**：大的一次一个，小的不受影响，两边加起来有个算得出来的上限。

## 2. 为什么不是排队

两种做法都能让大请求插到小请求前面。差在代价：

| | 按大小排队 + 队头阻塞 | 两条道（这份） |
|---|---|---|
| 大请求会不会被小的拖住 | 不会 | 不会 |
| 小请求会不会被大的拖住 | **会**（大的一排队，小的就在后面等，超时 429） | 不会 |
| 内存上限 | 算得出来，但要看排队的那一瞬间 | 算得出来，是两个数加起来 |
| 机制 | 一个等候队列，按大小插队 | 一个「一次一个」的门 + 一个字节池 |

「让路」是用户**不要**的那一面：他要的是大请求别被小请求挤掉，不是小请求给大
请求让路。两条道正好是反过来的那个方向，而且更简单 —— 没有队列，没有插队，
没有「队头卡着后面全堵」的那种状态。

## 3. 怎么分类

分类在**读身体之前**做，用的是 `Content-Length`：

| Content-Length | 去哪条道 |
|---|---|
| > 64 MiB | 不用分道了 —— 413（已有，`maxBodyBytes`） |
| > `body_small_mb`（默认 4 MiB） | **大道** |
| 不知道（分块传的，`-1`） | **大道**（宁可慢，不能让内存被撑破） |
| ≤ `body_small_mb` | **小道** |

分块传的按大道算：客户端没说多大，那就当它大。这是保守的那一边 —— 判错了的
代价是大请求慢一点，判错了另一边（小请求混进大道）的代价是几十兆的内存。

## 4. 准入的顺序

```
1. 413 的检查（已有）：Content-Length > 64 MiB 就拒了，连读都不用读
2. 道的门：大道拿「一次一个」的位；小道从字节池里占它的大小
3. 并发闸门（已有）：总并发 N
4. 读身体
5. 问上游，把答转给客户端
```

**道的门在并发闸门之前**，理由是并发闸门那 20 个位是共享的：如果大道排在并发
闸门后面，20 个大请求会把 20 个位全占住（它们在等大道那个位），小请求连闸门
都进不去 —— 那 19 个小请求就没了。放在前面，大请求在等闸门的时候只占着大道的
那个位，19 个小位照常空着。

道的门拿不到的时候，等 `concurrency.wait`（默认 10s），等不到就 429 带
`Retry-After` —— 跟并发闸门一样的规矩。

## 5. 两条道各是什么

### 大道：一次一个

一个位，同时只有一个大请求在里面。它的身体最大 64 MiB（`maxBodyBytes`），
所以大道最多占 **64 MiB**。

### 小道：一个字节池

小身体占它自己的大小（乘以拷贝数，见 §6）。池子上限是
`concurrency.body_budget_mb`（默认 80 MiB）。

池子空着的时候总是放一个进来 —— 哪怕这个身体比整个池子还大（配置写小了），
不然它永远等不到，池子空着它也进不来。

## 6. 内存账

在飞的身体占的字节：

| | 占多少 |
|---|---|
| 大道 | 1 × 64 MiB = **64 MiB** |
| 小道 | 池子上限 = **80 MiB** |
| 合计 | **144 MiB** |

跟用户算的一样：「19*4mib也就不到80MIB」—— 80 MiB 的小道装得下 19 个 4 MiB 的
小请求（大道占掉一个并发位），64 MiB 的大道装一个。**144 MiB。**

**拷贝数**：OpenAI 和 Codex 的身体要转成 Anthropic 的形状（`convert.ToAnthropic*`），
那是**第二份** —— 转换的那一刻两份都在。小道占的字节因此是两倍：

| 客户端 | 大道 | 小道 | 合计 |
|---|---|---|---|
| Anthropic（`/v1/messages`） | 64 MiB | 80 MiB | **144 MiB** |
| OpenAI / Codex | 128 MiB | 80 MiB | **208 MiB** |

（那一行是这份设计里唯一比用户算的大的地方 —— 转换的那份拷贝是原有的，不是这
份设计加的。）

这两行后来是**量过的**，见下一份：
`docs/superpowers/specs/2026-11-21-mmxcode-body-memory-design.md`
（一个 63 MiB 的身体进来，内存涨 378 MiB —— 六份拷贝；改完涨 63 MiB。144 MiB
这个数从那天起才是真的。）

还有一层：身体从读进来到答写完，一直活着（Go 的 `body` 和 `upBody` 两个变量
指着它）。所以「道」和「池」上的那份额度，也是到请求做完才还。

## 7. 什么时候还

请求做完的时候（`handleChat` 结束），大道那个位和池子上占的字节一起还回去。

**不是「发到上游就还」**：答案还在流的时候，身体那份内存还没释放（`body` 和
`upBody` 都指着它，`resp.Request.Body` 也指着它）。先还了额度再放内存进来，那
是账做假 —— 池子会以为空着，实际不是。用户原话是「发送到上游的瞬间解锁」，
那说的是**大请求别占着位**：而它占位期间内存本来就在，所以按做完还，账和内
存是一对一的。

## 8. 配置

```yaml
concurrency:
  # 多大的身体算小：超过它算大身体，一次只让一个进来
  body_small_mb: 4
  # 小身体同时在飞的总字节（80 MiB ≈ 19 × 4 MiB）
  body_budget_mb: 80
```

| 键 | 默认 | 意思 |
|---|---|---|
| `concurrency.body_small_mb` | `4` | 多大的身体算小。配 0 按 1 算（配 0 的话每个请求都是大身体，那不是关掉，是坏了） |
| `concurrency.body_budget_mb` | `80` | 小身体同时在飞的字节上限。**0 = 不限**（跟 `total_max` 一个规矩：那时候只剩并发闸门管着） |

## 9. 行为变了的地方

1. **大请求会等**（最多 `concurrency.wait`），等不到 429 带 `Retry-After`：
   「the gateway is busy: another big request body is in the air」。
2. **小请求会等**（字节池满了），等不到 429 带 `Retry-After`：
   「the gateway is busy: too many request bodies are in the air」。
3. 429 多了一种，客户端能分出来是哪一种忙。
4. **请求的顺序变了**：道的门在并发闸门之前，所以一个大请求在等并发位的时候，
   占着大道的位，小请求照常走。
5. OpenAI / Codex 的小身体占两倍的字节（转换的那份拷贝）。

## 10. 不做什么

- **不做「按大小排队」**：那是上一版的做法，用户已经换了。
- **不改 `maxBodyBytes`**：还是 64 MiB。
- **不砍 OpenAI/Codex 的那份拷贝**：那是另一个活儿（顺带能把 §6 那一行收回
  144 MiB）。
- **不动回包那边**：那是 `2026-11-21-mmxcode-upstream-body-limit-design.md` 的
  事。

## 11. 怎么量

1. **一个大请求 + 19 个小请求同时打进来**：内存峰值 ≈ 144 MiB，不更高。
2. **两个大请求同时打进来**：第二个等（或者 429），内存峰值还是 144 MiB。
3. **小请求把池子占满**：后来的小请求等，池子的字节数不超过上限。
4. **分块传的请求**：走大道（一次一个）。
