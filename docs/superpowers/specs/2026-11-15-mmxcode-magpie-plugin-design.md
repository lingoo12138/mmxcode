# mmxcode 接进 magpie —— 设计文档

日期：2026-11-15
状态：待评审

## 1. 目标与范围

### 1.1 一句话

做一个 **magpie 插件**，把我们自己的 mmxcode 网关变成 magpie 里的一个 provider：聊天走网关（轮转、多账号、故障转移都在网关里），余额卡片问网关要（一次请求答完，不逐个账号去问 MiniMax）。

网关那一侧配套改四件事：读额度只碰热账号、读额度有预算有并发、额度用完有标记有兜底、签到给的积分立刻进卡。

### 1.2 为什么现在做这个插件

参考插件 [`@magpie-community/opencode-minimax-auth`](https://github.com/magpie-community/plugins/blob/main/packages/minimax)（下称"参考插件"）在 magpie 里的用法是：**magpie 自己拿着账号的令牌，逐个账号去问 MiniMax** —— 余额、计划、窗口、账本，每样都要签名请求。

账号一多，这条路就两个毛病：

1. **卡死**：一个账号要问 4~5 个请求（membership、计划窗口、账本批次），N 个账号就是 4N~5N 个请求；magpie 的额度卡片是等着这些请求全部回来才画得出来的。
2. **多账号的账拼不起来**：magpie 看到的是一堆账号各自的额度，没有一个"这个网关还剩多少"的总数。

我们已经有网关了：账号、令牌、轮转、签到、读额度全在里面，额度卡片也是一个 HTTP 请求就答完（`GET /v1/usage`）。所以插件这一版只做一件事：**把 magpie 指到我们的网关上**，让查询都留在网关里。

这不是"再写一个 minimax 插件"，是"给网关写一个插头"。

### 1.3 范围内

**插件**（`packages/mmxcode/`，magpie-community/plugins 的包规矩）：

- provider id `mmxcode`：聊天（Anthropic 协议）、模型列表、余额卡片
- 签入方式：网关地址 + 网关的聊天 key
- 会话 id 传给网关（`X-Session-Id`），让网关能把一段对话黏在一个账号上
- 声明 `magpie.maxConcurrency`

**网关**（Go）：

- 热账号：只读正在被用着的账号的额度
- 每一趟读额度有并发、时限、预算、排序、单账号去重
- 额度用完：立刻标记（窗口组粒度）+ 后台读一次改标记 + 兜底
- 签到成功：读一次额度；读到的数说有额度就清掉「用完」标记
- 并发：每个 mcode 账号同时 1 个请求；网关总并发 = max(账号数/5, min(账号数, 3))
- `GET /v1/models` 补上 magpie 需要的模型元数据
- `GET /v1/usage?refresh=1` 的现读走热账号、有预算

### 1.4 范围外（明确不做）

- **magpie 里的签到按钮**。签到是网关自己的活（每天一趟 + 后台页面手动点）。magpie 要有签到按钮，网关就得再开一个聊天 key 也能用的 `/v1/checkin` —— 不做。
- **参考插件的工具**（Matrix 工具、web search、MCP 媒体）。那些是拿账号令牌直接打 MiniMax 的接口的，跟"查询都留在网关里"相反。
- **中国站**（`minimax.cn`）。网关是国际站。
- **替换掉 magpie 自带的 minimax-code-global**。两个 provider 并存：global 还在，插件是另一个 id（`mmxcode`）。要不要卸掉 global 是用户的事。
- **把 magpie 做成我们网关的上游**。方向是反的：网关是 magpie 的下游。

### 1.5 三个角色

```
magpie ──插件 mmxcode──▶ mmxcode 网关 ──▶ MiniMax Code 的账号们
   │  聊天 /v1/messages      │  轮转、换号、签到、读额度
   │  模型 /v1/models        │
   └─卡片 /v1/usage ─────────┘
```

插件里**没有** MiniMax 的账号、令牌、签名 —— 那些全在网关里。插件只认得两样东西：网关的地址，和一把聊天 key。

## 2. 插件（magpie 那一侧）

### 2.1 包的样子

放在我们仓库的 `packages/mmxcode/`，按 magpie-community/plugins 的规矩写（以后想提 PR 上游，差的东西一眼能看出来）：

| 文件 | 是什么 |
|---|---|
| `package.json` | 名字、版本、`main: ./index.mjs`、`type: module`、`magpie.maxConcurrency` |
| `index.mjs` | 插件本体，一个导出的异步函数 |
| `README.md` | 中英文各一份：它是什么、怎么签入、怎么装、它跟 global 那个差在哪 |
| `LICENSE` | MIT（上游的规矩） |
| `index.test.mjs` | 钩子的测试（对着一个假的网关跑） |

装法（不装进 npm，就地加载）：

```sh
magpie plugin add ./packages/mmxcode
```

包名先用自己的（`mmxcode-auth`）；要上游再按上游的命名改（`@magpie-community/opencode-mmxcode-auth` 之类）。

### 2.2 provider 的声明

```js
config: async (cfg) => {
  cfg.provider ??= {}
  cfg.provider[PROVIDER] ??= {
    name: "MMXCode",
    npm: "@ai-sdk/anthropic",   // 网关讲 Anthropic 的 /v1/messages
    api: defaultBase + "/v1",
    models: { /* 兜底的那几行，见 §2.5 */ },
  }
}
```

- provider id：`mmxcode`（跟 `minimax-code-global` 分开 —— 频道是同一个，但这是我们自己网关的 provider，id 不能撞）。
- `npm: "@ai-sdk/anthropic"`：magpie 用 Anthropic 的 SDK 跟网关说话。网关的 `/v1/messages` 就是原生 Anthropic 形状（上游 MiniMax Code 也是这个形状，网关不改写）。
- `api` 只是**没签入时的默认值**；签入以后 `loader` 给的 baseURL 说了算（那时是用户填的网关地址）。

### 2.3 签入

一个 `api` 类型的签入方法（magpie 的 API key 签入，和参考插件的 device 签入不同 —— 我们签的不是 MiniMax，是自己的网关）：

```js
methods: [{
  type: "api",
  label: "MMXCode 网关",
  keyless: true,               // magpie 自己不问 key，我们自己问
  prompts: [
    { type: "text", key: "base", message: "网关地址（默认 http://127.0.0.1:8080）" },
    { type: "password", key: "key", required: false, message: "聊天用的 key（后台 /keys 申请的；网关一把 key 都没有时可以留空）" },
    { type: "text", key: "label", required: false, message: "这个名字（magpie 里认这个账号用）" },
  ],
  async authorize(inputs) { /* 见下 */ },
}]
```

`authorize` 做一件真事：**打一次网关的 `GET /v1/models`**，看它答不答。

| 答 | 说什么 |
|---|---|
| 200 | 成了 |
| 401 / 403 | 「网关拒绝了这把 key —— 它开的是哪扇门？聊天接口要聊天 key，后台登录 key 也行」 |
| 连不上 | 「网关连不上：<地址>」 |
| 别的 | 「网关答了 HTTP <码>」 |

签入不成功就说清楚，不留一个半签入的账号。

### 2.4 聊天：会话 id 怎么带

**magpie 不在 HTTP 请求里带会话 id** —— 它把会话 id 交给插件：`chat.headers` 钩子的 `input.sessionID`（magpie 的 conversation id，一段对话里不变）。

所以插件要加这个钩子：

```js
"chat.headers": async (input, output) => {
  if (input.model?.providerID !== PROVIDER) return
  output.headers["X-Session-Id"] = input.sessionID
}
```

网关认的头是 `X-Session-Id` / `X-Conversation-Id` / `X-Session-Id-Codex` / `Session-Id`（第一个优先）。有了它，网关把一段对话黏在一个账号上；没有它，网关退回"系统提示 + 第一条用户消息"的哈希 —— 能用，但两个用户的第一句话一样就会撞成一个会话。magpie 一定给这个 id，所以正常走的是第一条。

### 2.5 模型列表

`provider.models` 去网关问：`GET /v1/models`。

网关现在给的是 id（`MiniMax-M3.1-Flash`、`MiniMax-M3`），magpie 还要 context/output、能不能读图、思考档位 —— 所以**网关的 `/v1/models` 要补上这些字段**（见 §8.1），插件照着摆成 magpie 的行。

答不出来（网关连不上、答的不是列表）时，插件摆 `config` 里那几行兜底的（跟参考插件的做法一样：magpie 手里那份名单留着）。

### 2.6 余额卡片

`auth.usage` 是 magpie 自己的钩子（OpenCode 不理它）。它问网关：`GET /v1/usage?refresh=1`（带上 refresh 是要现读；现读是有预算的，见 §3.4 —— 卡片不会等）。

网关答的已经是 magpie 的卡片形状：

```json
{
  "plan": "Token Plan M3",
  "until": "2026-12-01T00:00:00Z",
  "balance": "437.5 credits",
  "windows": [ { "name": "主号 · Credits", "used": 12.5, "display": "62.5 / 500", "amount": 62.5, "limit": 500, "unit": "credits" } ]
}
```

插件**原样转交**（magpie 认得这几个字段）。网关那边一个 mcode 账号 = 卡片上一个窗口，balance 是所有账号加起来 —— 卡片是整个网关的账。

卡上**不写读到的时间**：magpie 的卡片只留它自己的字段，多出来的东西塞进去只会让它变形。

### 2.7 并发上限

`package.json` 里声明：

```json
"magpie": { "maxConcurrency": 8 }
```

**要说清楚它限的是什么**：magpie 眼里"一个账号"= 一次签入 = **我们的整个网关**。所以它限的是"这个网关同时几个请求"，**不是**"每个 mcode 账号几个"。防的是一堆请求砸到网关；真正的"每个 mcode 账号同时 1 个"在网关里做（§6）。

用户可以在 magpie 里改这个数（用户设的赢过插件声明的）。

### 2.8 插件不做的事

- 不签到（§1.4）。
- 不带 MiniMax 的账号令牌 —— 插件永远不跟 MiniMax 直接说话。
- 不搬参考插件的工具、搜索、媒体。
- 不做多网关：一个 magpie 账号 = 一个网关。要连两个网关就签入两次，magpie 里有两张卡。

## 3. 网关：读额度只碰热账号

### 3.1 什么叫热

**热账号 = 最近 `hot_window`（默认 5 分钟）里被轮转用过的账号。**

聊天成功一次就算一次"用过"。用量的计数放在内存里（一个带窗口的计数器，最多记 200 个账号，过期的自己清掉）—— 它是"刚刚"的账，不是账本，不需要落库。

### 3.2 每一趟读哪些账号

```
该读的 = 从没读过的 ∪ 热的 ∪ 签到待补的 ∪ 标记到期的
```

| 从哪来 | 是什么 | 为什么 |
|---|---|---|
| 从没读过的 | 没有快照的账号 | 卡上是"所有账号的额度"——没读过的账号卡上根本没有它；而且在选号规则里"读到的余额"排前面，没读过的账号永远排最后（死锁）。**每个账号至少读一次**，这是硬要求。 |
| 热的 | 最近被用过的 | 它的额度最可能刚变 |
| 签到待补的 | 签到成功、账本还没读到的 | 见 §5.3 |
| 标记到期的 | 窗口回来时刻到了的 | 见 §4.5 |

后三类都能从现有的表里算出来（快照、检查到账记录、耗尽标记），不需要新表。

### 3.3 一趟读的控

| 控 | 默认 | 为什么 |
|---|---|---|
| 并发 | 4 | 并发是读得快，不是读得多 |
| 每个账号的时限 | 15 秒 | 一个卡住的账号不能拖住整趟 |
| 一趟的预算 | 30 秒 | 预算用完就停，剩下的下一趟接着读 |
| 一趟最多读几个 | 6 | 预算 ÷ 时限 |

**排序**：签到待补 → 标记到期 → **从没读过的** → 热（次数多的先）。

为什么这么排：

- 签到待补的卡上现在是错的；
- 到期的马上要回轮转；
- **从没读过的排在热的前面** —— 它是一次性的活儿，排在后面就永远排在后面（每一趟都有热的账号占着位置），那就是 §3.5 说的死锁；
- 热的刚变过，但它们每一趟都会被读到（还在用就一直热），晚一轮没关系；
- 冷账号不在这一趟里：§3.2 那四类之外的账号这一趟不读（见下面一段）。

**冷账号不在这趟里**。冷账号的数是旧的，读它要三四个上游请求，而它可能压根不需要 —— §3.5 说它会自己醒过来：旧数是高估，轮转反而会挑它，它被用到、变热，那时才读。一直读冷账号，一趟就把名额占满，从没读过的账号反而永远轮不上。

**到期读一次**。标记到期（§4.5 A）的账号只读一次：到期之后还没有人读过它，它才是"到期"；读到之后它就不再是了（数已经变新）。不然一个用完过的账号会一辈子排在名单前面，每一趟都被读一遍。

**单账号去重**：同一个账号同一时刻只读一次（签到那一趟和热的那一趟可能撞上）。

**签到那一趟读不完，剩下的怎么办**：签到 100 个账号、一趟只读 6 个 —— 剩下 94 个在"待补"名单里（§5.3），下一趟接着读（待补排在最前面，所以几分钟内就清完了）。

### 3.4 卡片那条路（refresh=1）

`GET /v1/usage?refresh=1` 现在是**顺序读所有账号**再回答 —— 这就是卡死的来源。

改成：只现读**最热的 2 个**（5 秒预算），其余用上一次读到的数。

所以卡片**永远几秒内回来**。数字是"尽可能新 + 其余是上次读到的" —— 这是"只做热数据"的代价，说清楚。

### 3.5 每个账号至少读一次

不是可选项，是两条硬要求：

1. **卡上是所有账号的额度** —— 没读过的账号在卡上根本不存在。
2. **选号不能被"没读过"锁死** —— `bestAccount` 把"读到余额的"排在前面，没读过的永远排最后 → 永远挑不到 → 永远不读 → 永远挑不到。

而且它自己会醒过来：冷账号的旧数是**高估**（积分只会往下走），它比热账号的数大 → 轮转反而会挑它 → 它被用到 → 变热 → 被读 → 真相露出来。

## 4. 网关：额度用完的标记与兜底

### 4.1 标记

上游答"用完了"的那一刻（rotator 的 `ActionFailover`）就标记，不等下一轮读额度。

- **粒度**：账号 × **窗口组**。这个模型组用完了，换个模型还能用（现有的粒度，保持）。
- **记在哪**：`exhausted_windows` 一行，带"什么时候回来"。

### 4.2 什么时候回来（until）怎么定

| 情况 | until |
|---|---|
| 上一次读到的窗口时刻，在将来 | 就用它 |
| 取不到（没有快照/窗口没读到） | **冷却时间**（`rotation.exhausted_cooldown`，默认 5 分钟） |
| 取到了，但**已经在过去** | **当没有** → 冷却时间 |

第三条现在是个洞：代码把过去的时刻也照写不误，而 `isExhausted` 看到过去的时刻就当"没耗尽" —— 结果这个账号立刻又回到轮转里，客户端下一次还是撞上它。

### 4.3 后台读一次，改标记

标记完，在后台读一次那个账号的额度（不阻塞客户端）：

- 读到了 → 把标记改成**真正的**窗口时刻（后台改）。
- 读不到 → 标记留着（冷却）。

### 4.4 请求内换号 / 请求间改绑

- **同一个请求里**：上游答"用完" → 标记 → **换号重试**（最多 `rotation.max_attempts` 次，默认 3）→ 客户端拿到的是另一个账号的答案，看不见这个账号的失败。只有**所有**账号都空了，客户端才看见额度用完。
- **下一个请求**：绑定账号被标记了 → 挑一个新的账号 → **改绑**（`sessions` 表更新）。
- **历史不会丢**：Anthropic 协议每个请求都带全部消息；换账号后新账号收到同样的会话 id（对它来说是新对话）+ 完整历史。

### 4.5 恢复点

| 坏状态 | 谁把它变好 |
|---|---|
| 标记的 until 未知或已过期 | **A** 窗口时刻到了 → 标记自然过期 → **到期读一次** → 数变新，账号回轮转<br>**B** 签到给了积分 → 读账本说有额度 → **清标记** → 回轮转<br>**C** 冷却到期又被选中 → 又用完 → **再读一次**（§4.3）→ 这次读到真的时刻 → 标记准了 |

**A（到期读一次）**是"该读的账号"里的一类（§3.2）：标记到期的账号会被读到，读完它的数就是新的。

## 5. 网关：签到给的额度

### 5.1 签到成功 → 读一次

签到给的积分是**账本池**里的，卡上的 balance 就是账本剩余之和。签到完不读额度，卡上的余额还是签到前的旧数。

而且**签到的账号大概率是冷的** —— 一天签一次、平时不用，按"只碰热账号"它永远不会被读。**签到完不读额度，卡就是错的，而且不会自己变对。**

所以：

| 谁签的 | 怎么读 |
|---|---|
| 调度器每天那一趟 | 签完把**签到的账号凑成一批**，一次有预算地读（§3.3 的那套） |
| 后台页面上单账号的签到按钮 | 读完这一个账号的额度再回答（人在等，快） |

### 5.2 读到的数说话：清不清「用完」标记

签到给的积分**能救活**一个"额度用完"的账号。不处理的话，它会一直待在外面的轮转之外，直到窗口回来（最长 7 天）—— 白扔一个账号。

清不清，用**读到的数**决定，不猜：

| 读到的数 | 做什么 |
|---|---|
| 账本还有余额，**或** 计划窗口还有余量 | 清掉这个账号记的「额度用完」标记 → 它回到轮转里 |
| 账本是 0，计划窗口也都用完了 | 标记留着，它继续在外面待着 |
| **读不到** | **不动标记**（宁可少用一个账号，也不要把一个用完的账号放回去让客户端撞它）→ 进"签到待补"名单，下一趟再读 |

清错了的代价：客户端撞一次、我们再记一次（每天一次，可接受）。

### 5.3 签到待补

"签到成功但账本没读到"的账号，下一趟要再读。它是**算出来的**：检查到账记录比这个账号最新的快照还新 → 待补。不用新表。

读失败的那一次也算待补，但只重试一阵（签到后 10 分钟内）：一直重试会把整趟的名额占住，从没读过的账号就永远轮不上。过了这一阵，它就等下一次签到、或者等它被用到（变热）再说。

## 6. 网关：并发

### 6.1 每账号 1

**每个 mcode 账号同时只跑 1 个请求。**

- 挑账号时必须**避开在飞的账号**（不然第二个请求又落它身上，额度还是掉得快）。
- 满了怎么办：**换号，但不改绑**。绑定是"这个会话的家"，不能因为一次忙就搬走（否则并发会话互相推来推去）。
- 于是负载自然摊开：忙的账号暂时少接会话。

网关在飞请求的计数放在内存里（每个账号一个数）。

### 6.2 总并发

```
总并发 = max(floor(可用账号数 / 5), min(可用账号数, 3))
```

**可用账号数** = 状态是 active（签入中）且没有被标记用完的账号数。账号用完了不算 —— 它现在也接不了活。

| 可用账号数 | 总并发 |
|---|---|
| 1 | 1 |
| 3 | 3 |
| 5 | 3 |
| 12 | 3 |
| 100 | 20 |

（`floor(可用账号数/5)` 是"只用五分之一，留着四分之五"；`min(账号数, 3)` 是给小规模兜底 —— 5 个账号只跑 1 个太憋屈。）

**为什么是"1/5 在用，4/5 留着"**：100 个账号同时只用 20 个 → 这 20 个把额度用完了，还有 80 个是满的可以接。一个接一个地烧，而不是所有账号一起烧到没。

超了的请求**排队等**（等前面的让出位置），等不到（客户端自己超时了）就 429 带 `Retry-After`。

### 6.3 挑账号要避开在飞的

rotator 要能问一句"这个账号现在忙不忙" —— 跟现有的 `RemainingFor` 一个路子：池接口加一个查询，网关把在飞的计数报给它。

（`bestAccount` 的"余额最多"规则保持不变。有了"每账号 1 个在飞"，负载自然摊开；"每个账号至少读一次"保证没读过的账号不会永远排最后。）

### 6.4 没有空闲账号就等

可用账号都忙（比如只有 1 个账号）→ 等前面的请求结束，而不是报错。

### 6.5 magpie 那边的 maxConcurrency

见 §2.7：它限的是"这个网关同时几个请求"，跟"每个 mcode 账号几个"是两回事。两层一起兜。

## 7. 账号的状态与恢复点

| 状态 | 是什么意思 | 卡上 | 在轮转里吗 |
|---|---|---|---|
| **U 未读** | 从没读过账本 | 没有它 | 在（但挑不到，见 §3.5） |
| **H 热** | 最近被用过 | 数是新的 | 在 |
| **C 冷** | 一阵子没被用 | 数是旧的 | 在 |
| **X 用完** | 被记了「额度用完」 | 显示用完 | **不在** |
| **P 待补** | 签到成功，账本还没读到 | 数是旧的 | 在 |

三条线（签到 / 热 / 用完）的交叉：

| 交叉 | 会发生什么 |
|---|---|
| **用完 × 热** | 在热的时候用完 → 标记 + 后台读一次（卡上看见它用完）→ 轮转跳过它 → 它变冷 → 它的数停在使用完那一刻（对的，它确实用完了）。那次读失败 → until 未知 → 冷却 → 冷却后又被选中 → 又用完 → 再读一次 → 这次读到真的时刻（§4.5 的 C） |
| **用完 × 签到** | 签到给积分 → 读账本 → 有额度 → 清标记 → 活了（§5.2）。读不到 → 不清，进待补，下一趟再读（§5.3） |
| **签到 × 热** | 签到的账号通常是冷的 → 签到后读的那一次就是最新的 → 卡上对。它不热 → 之后不更新，直到它被用到 |
| **三条一起** | 热 → 用完（标记 + 读）→ 冷；签到（积分到账）→ 读 → 清标记 → 活了 → 但它不热 → 下次被选中 → 聊天成功 → 热 → 继续被读。自洽 |

## 9. 配置

```yaml
usage:
  refresh:
    hot_window: 5m      # 多久算热
    scan_every: 30s     # 多久扫一遍该读的账号
    concurrency: 4      # 一趟同时读几个
    timeout: 15s        # 每个账号的时限
    budget: 30s         # 一趟的总预算
    batch: 6            # 一趟最多读几个
    card: 2             # 卡片现读读几个
    card_budget: 5s     # 卡片现读的预算
```

并发（§6）：

```yaml
concurrency:
  per_account: 1        # 每个 mcode 账号同时几个
  total_ratio: 5        # 总并发 = 账号数 / 这个
  total_min: 3          # 小规模兜底：min(账号数, 这个)
  wait: 10s             # 等不到位置就 429
```

## 10. 测试与验证

**Go 侧**（单测）：

- 热账号计数：窗口过期就掉出去
- 批量读：排序、并发上限、预算用完就停、单账号去重、读失败不挡别的
- 额度用完：过去的 until 当没有 → 冷却；后台读到了 → 标记改对；读不到 → 标记留着
- 签到：读到有额度 → 清标记；读到没有 → 标记留着；读不到 → 待补
- 并发：在飞的账号不被挑；总并发上限；没有空闲账号就等
- `/v1/models` 的元数据；`/v1/usage?refresh=1` 只读热的

**插件侧**（`node --test`，对着一个假的网关）：

- 签入：网关答 200 / 401 / 连不上，各自说什么
- `usage`：网关的卡片原样转交
- `provider.models`：网关的名单摆成 magpie 的行；网关答不出来时摆兜底的
- `chat.headers`：加 `X-Session-Id`

**本机**（不起 docker）：
