## 1. 原话

> 我们的账号可以分阶段性加载进内存，我们可以根据设置的并发数，动态加载账号池，比如 n 个并发，我们可以加载 n*n 个账号。遇到账号额度用完，我们就补充新的冷账号进来，把额度用完的账号打标记入库，这样也不会吃太多内存。然后我们为了提高缓存命中率，我们一个聊天窗口是要保持在一个账号里面，除非账号没有额度了，不然我们的同一个 session 窗口就始终打到同一个账号去。结合我们的热账号刷新消耗积分的后台机制，我希望能以最小的代价获取最实时的信息。

## 2. 拆成五件事，和现在的代码对一遍

| # | 想法 | 现在的代码 | 差在哪 |
|---|---|---|---|
| 1 | 按并发数动态加载账号池进内存（n 个并发 → n\*n 个账号） | **没有池**。每次 `Pick` 都把 `accounts` 整表从 SQLite 读一遍（`internal/rotator/rotator.go:316` → `internal/store/store.go:1416`），`exhausted_windows` 也整表读（`rotator.go:320`） | **全新的**：内存里一个**有上界**的池 |
| 2 | 额度用完 → 补充冷账号 | 上游答用完 → 写 `exhausted_windows`（`internal/store/store.go:2054`）→ 跳过它 | 标记有了，**从池里摘掉 + 补冷号**没有 |
| 3 | 用完的账号打标记入库，不吃内存 | 标记本来就在库里 | 已有；新的是「出池即入库，不常驻」 |
| 4 | 一个 session 始终打同一个账号，除非额度用完 | `sessions` 表绑定（`store.go:2132`），粘性策略默认（`rotator.go:337-395`），额度用完就改绑 | **已有，语义正是用户说的**（忙 ≠ 没额度，不改绑） |
| 5 | 结合热账号刷新，最小代价拿最实时信息 | `usage.Round` 只读四类账号：签到待补 / 标记到期 / 从没读过 / 热（`internal/usage/round.go:104-226`），冷账号不读 | 已有；缺的是**池里那批号的数要准**，跟池子对齐 |

一句话：**想法里最旧也最实的是「会话黏性 + 耗尽标记」，这两块已经有了；真正新的是「内存里的分级账号池」。**

## 3. 现在的账：每个聊天请求读三遍全表

- `rotator.Pick` → `pool.Accounts(ctx)`（`rotator.go:316`）→ `store.ListAccounts`（`store.go:1416-1437`）：`SELECT … FROM accounts ORDER BY created_at`，整表。
- 同一趟 → `pool.Exhausted(ctx)`（`rotator.go:320`）→ `store.ListExhausted`（`store.go:2082-2107`）：整表。
- 挑号还要按剩余积分排 → `pool.RemainingAll`（`internal/gateway/gateway.go:294-318`）→ `store.LatestUsageSnapshots`（`store.go:1935-1962`）：**所有账号的最新快照，连 `windows_json` 一起**，整表。这是三趟里最贵的一趟（2.2KB/号），而选号只需要 `remaining`。
- 账号行本身是小的（`store.Account`，`store.go:87-98`：id/name/user_id/email/status/proxy_group/proxy_url/last_error/两个时间戳，**没有 token**），所以内存不是被账号行撑爆的，是被**每个请求都重扫一遍**拖慢的。
- 号越多越贵：100 个号是 100 行，1 万个号就是 1 万行 × 每个请求（§6.2 有数）。

## 4. 想法长什么样（还没定，见 §5）

### 4.1 池的边界

- **池里放什么**：账号行 + 最新快照的剩余积分 —— 就是选号要用的那两样。耗尽标记
  不放：额度用完的号当场出池，池里没有用完的号，也就没有标记要记（标记的真相
  在库里）。
- **池多大**：`总并发 × 放大倍数`。用户给的是 n\*n（n = 并发数）。放大倍数要能配，还得有绝对上限（不然并发一大就爆了）。
- **池的上面**：库里的活跃账号总数。库里没有有额度的号了，池就那么多。

### 4.2 进池：读一次额度

**进池前读一次额度** —— 一次上游读。这一次读出来的数就是准的，池里这个号的数从这一刻起可信。

冷账号只读这一次：它在池外的时候没人用它，它的数旧一点没关系。

### 4.3 在池：跟着热账号的节奏读

池里就是「热账号」这一档（`usage.Round.Targets` 的第四类）。后台每轮（`usage.refresh.scan_every`，默认 30s）读池里那几个，**池外的号不读**。

这一条合起来就是用户说的那句：**代价正比于池的大小（n\*n），而不是库里账号的总数**。100 个号和 1 万个号，读额度的开销一样。

### 4.4 出池：额度用完

```
上游答「用完」
  → 写 exhausted_windows（直到什么时候回来 = 窗口时刻，没有就冷却时间）
  → 从池里摘掉这个号
  → 补一个冷号进来（进池前读一次额度）
  → 绑在这个号上的 session 改绑到新号
```

改绑不丢上下文：Anthropic 协议每个请求带全量历史，新号收到同样的 session id（对它来说是新对话）+ 完整历史（现在的代码就是这么做的，`rotator.go:383-395`，`Plan.Rebound`）。

### 4.5 会话黏性

| 绑定的号怎么了 | 怎么办 |
|---|---|
| 还在池里、还有额度 | **一直用它** —— 这就是缓存命中率高的原因 |
| 额度用完 / 出池 | 改绑到新号（历史照带） |
| 只是忙 | **不改绑**，换号答这一次（忙 ≠ 没额度）。现在的代码就是这样（`rotator.go:363-372`） |
| 号被签出 / 删了 | 改绑（`rotator.go:346-349`） |

## 5. 要定的事（我先给个建议，等拍板）

| 问题 | 我的建议 |
|---|---|
| 放大倍数 n\*n 太大 | 见 §5.5：内存根本不是约束（每个账号 395 字节），倍数要按**可用性**定，建议 **2** |
| 池是每进程一个 | 是。网关单进程，池就放在 rotator 旁边 |
| 进池时读额度失败 | **不进池**：数不明就挑不到（现在的语义就是这样，「没读到」排在最后），但也别占着池的位置 |
| 池里的号数要多准 | 进池读一次 + 在池期间按热账号节奏读。出池就不管了（等 `until` 到点再说） |
| 出池的号什么时候回来 | `exhausted_windows` 的 until 到点 → **重新走一遍「进池」**（读一次额度 → 进池），不是自动回池 |
| 冷号补进来的顺序 | 按剩余积分多、最久没用过 —— 跟现在 `bestAccount` 一个口径，别搞出第二套 |
| 池和卡片的数对不上 | **本来就是两件事**：卡片是全池的账（所有账号的快照，`usage.Aggregate`），池只管选号。别拿池里的数去画卡 |
| 重启后池是空的 | 得从库里重建：先用旧快照顶上（能挑号），再补一轮读额度把数读准 |

## 5.5 内存账：200MB 怎么分（本机实测，2026-11-17）

### 5.5.1 量出来的事实

跑着的网关（100 个账号、11 个会话、SQLite 4 个连接）：

```
Working Set 40.4 MB   Private 59.8 MB   线程 14
```

固定开销 ≈ **40–60MB**（Go 运行时、SQLite 页缓存 —— 4 个连接 × 2MB、HTTP、TLS）。200MB 里能给账号的 ≈ **140MB**。

每个账号在内存里占多少（拿真实的 struct 复刻，10 万个量进去量堆）：

| 放什么 | 每个账号 | 1 万个号 | 10 万个号 |
|---|---|---|---|
| **池条目**（账号行 + 剩余积分 + map 索引） | **395 B** | 3.8 MB | 38 MB |
| **卡片那条路**：所有账号的最新快照（没有计划窗口） | 120 B | 1.2 MB | 12 MB |
| **卡片那条路**：所有账号的最新快照（**有计划窗口**，每个号 ~2.1KB 的 windows_json） | **2168 B** | 21 MB | **207 MB** |

**结论一：池不是内存的大头。** 就算池里放 10 万个号，也只有 38MB；1 万个号 3.8MB。内存从来不是池的限制。

**结论二：真正的雷是卡片那条路。** `Store.LatestUsageSnapshots`（`internal/store/store.go:1935`）在**每一次卡片请求**里把**所有账号**的最新快照（连 `windows_json` 一起）读成一个 slice。10 万个有计划的账号 = 一次请求 207MB —— 200MB 的预算一次卡片就吃光了。跟池没关系，是现在就该分开的事：卡片的余额要所有账号的 `remaining`（120B/号），计划窗口只有**上卡的那十来个号**需要看。

**结论三：池里绝对不放 `windows_json`。** 放了就从 395B 变成 2168B，内存账翻 5 倍。池只放选号要用的两样：账号行、剩余积分。

### 5.5.2 倍数定 2，不是 n\*n

倍数不是按内存定的（内存不管），是按**可用性**定的：

- **硬底线**：池 ≥ 总并发。每个账号同时只跑 1 个请求（`concurrency.per_account` 默认 1，`internal/config/config.go:275`），池比总并发小就是 `ErrAllBusy` → 429。
- **还要装下活跃会话**：会话钉在号上，钉住的号**不在池里**就会改绑（`rotator.go:346-349`：号不在 `accounts` 里 → 绑定可以换掉），缓存命中率就没了。所以池 ≥ 活跃会话数。
- **再留一倍备用**：额度用完要补号，补号前要读一次额度（上游调用，几百毫秒），这段时间那个位置空着。

→ **池大小 = max(总并发, 活跃会话数) × 2**

对着现在的数：总并发 = 100 个可用号 ÷ 5 = 20（`internal/gateway/busy.go:148-168`），活跃会话 11 → max = 20 → **池 = 40 个号 = 16 KB**。

**n\*n 在这个量级等于白做**：总并发 20 → n\*n = 400，但库里只有 100 个号 → 池 = 100 = 全量 = 现在整表读的行为。池存在的意义（选号不扫全表）就没了。倍数 2 时池是 40 个号，选号从 100 行降到 40 行，而且冷号留在库里不占内存。

### 5.5.3 上限：内存给的数是个安全网，不是约束

- 池的内存预算给 **32MB** → 32MB ÷ 395B ≈ **8.5 万个号**。这是个兜底上限，永远碰不到（总并发和活跃会话数都比它小）。
- 真正的上限是**有额度的活跃账号数**：池不可能大于库里能用的号。

### 5.5.4 200MB 的分账

| 用途 | 预算 | 现在 |
|---|---|---|
| 固定开销（Go + SQLite + HTTP） | 60 MB | 实测 40–60MB |
| 池（选号要的） | ≤ 32 MB | 16 KB（40 个号） |
| 卡片（全量 remaining + 上卡号的窗口） | ≤ 32 MB | 120B × 账号数 + 2.2KB × 上卡的那几个 |
| WAL、HTTP 连接、GC 余量 | 剩下 ~76 MB | WAL 现在 4MB |

按 200MB 倒推的硬上限：**有计划窗口的账号总数 ≤ 3 万**（3 万 × 2.2KB = 66MB，加上固定开销和 GC 余量是紧的）。要过这个数，得先把卡片那条路拆成两段读（见结论二）。


## 6. 200–1000 个号的规划

规模假设：个人使用，账号 200–1000 个，每个号 400–800 积分（实测 400/800），对话活跃会话几十到几百。

### 6.1 这个规模下，内存根本不是约束

| | 200 个号 | 1000 个号 |
|---|---|---|
| 池（395B/号） | 79 KB | 395 KB |
| 卡片一次全量快照（2168B/号） | 0.43 MB | 2.2 MB |
| 固定开销（实测） | 40–60 MB | 40–60 MB |

200MB 的预算在这个规模是**宽裕**的（用到 5MB 以内）。要省的不是内存，是**上游调用次数**和**每个请求的 DB 往返**。

### 6.2 性能：现在每个聊天请求要过三遍全表

`rotator.Pick` 一趟要问库三次（`internal/rotator/rotator.go:316-320`、`internal/gateway/gateway.go:294-318`）：

| 读什么 | 行数 | 每次请求的分配 |
|---|---|---|
| `ListAccounts` | 全部账号 | N × ~300 B |
| `ListExhausted` | 全部耗尽标记 | 小 |
| `LatestUsageSnapshots` | 全部账号的最新快照，**连 windows_json 一起** | N × ~2.2 KB |

**1000 个号 ⇒ 每个聊天请求约 2.6MB 的垃圾**（其中 2.2MB 是 windows_json，选号根本用不上它）。10 个请求/分钟就是 26MB/分钟的垃圾，全进 GC。

池化之后这三趟**全表读没了**（池在内存里），剩下一次会话绑定的 SELECT。**这是这个规模下最大的性能收益。** —— 不是真的归零：池的名单每次现给一份拷贝（池 400 个号 ≈ 70KB/请求，对比从前 2.6MB/请求，是几十倍的改善，但那是拷贝，不是零）。

### 6.3 池的大小

- **对外承诺的总并发要按池算**：`min(可用账号数/5, 池里能用的号)`。按库里的号承诺并发、池却没填满 = 一片 429。
- **池 = max(总并发, 活跃会话数) × 2**，上限 = 有额度的活跃账号数。
  - 200 个号：总并发 40 → 池 80
  - 1000 个号：总并发 200 → 池 400（内存 158KB）
- **冷启动不能靠读额度填池**：读额度是 6 个/30s（`usage.refresh.batch`），填满 400 个要 33 分钟。→ **填池用库里最后的数顶上，不等读**；读额度在后台慢慢补准。
- **池要先装对话绑着的号**（见 §6.8）：会话钉在号上，钉住的号不在池里就会被改绑，缓存命中就没了。所以填池的排队规矩是「最近活跃的对话绑着的号 → 从没读过的号（新导入的在前）→ 读得最早的号」。

### 6.4 时效性：读额度要花钱，策略是「读得少 + 让失败自证」

一次读额度 = 1 个 membership + 1~10 页 ledger = **2~11 个上游请求**（`internal/account/account.go:456-457`：每页 20 条、最多 10 页）。

**关键事实：积分只会往下走。** 池里没被读过的号，它的数字是**高估**的。高估的代价是：选号挑到一个其实已经用完的号 → 上游答「用完」→ 写 `exhausted_windows` → 换号重试。**这次失败恰好把标记写准了 —— 系统自愈**，代价是一个请求（重试上限 3）。

所以**不需要为了「选号准」而狂读额度**。读额度真正该做的只有五件事（有优先级）：

| 优先级 | 什么时候读 | 为什么 |
|---|---|---|
| 1 | **补号时**（新号进池） | 那个位置空着，等一次读（几百毫秒）不耽误别人；读完顺带验证号还能用 |
| 2 | **签到之后** | 签到给的积分是新的，不读卡就是错的（现在就有这个机制） |
| 3 | **标记到期** | 号要回池了，得先知道它现在还有没有额度 |
| 4 | **刚被用过**（热的） | 卡片要准它。热 = `hot_window`（默认 5 分钟）内被用过 |
| 5 | **卡片现读最热的 2 个** | 卡片永远几秒内回来（现在就有） |

**例外**：冷启动批量填池时**不读**（用旧数顶上）—— 等不起，而且旧数只是高估，撞空时 failover 自愈。

**能保证的时效性**：一个号刚被用过 → 下一趟（≤30s）读到。
**不能保证的**：从没被用过的号，它的数字是旧的。

一趟的预算（现在就是这些数）：并发 4、每趟最多 6 个、每 30s 一趟 → **12 个/分钟、720 个/小时**。这就是「时效性」的物理上限：1000 个号的池全刷准要 83 分钟。**所以只能保证「快被用的号准」，这就是「最小代价拿最实时信息」的确切含义。**

### 6.5 活跃性：池不能是一潭死水

- **只出池一种情况**：额度用完（写标记 → 出池 → 补号）。换出别的号要重读，贵。
- **池是按号算的**：一个组的额度用完了，那个号这一趟就出池 —— 别的组还有额度也不要（规格 §4.4）。rotator 那边的标记是按组跳过的（一个号的「video」组用完了，它还能答「general」），池里用不上那套：池里没有用完的号，也就没有标记可跳。这是这一版的简化，写下来免得后来的人当成 bug。
- **补号挑谁**：优先「有额度 + 最久没用过」（冷号优先 —— 老号已经被用熟了）。补号候选要包括三类：**签到待补的**（它有新的积分，不被用掉就过期）、**标记到期的**、**从没被用过的**。
- **签到的积分只有被选中才会被用掉**（否则 7 天过期）→ 签到待补的号应该优先补进池，这是签到机制真正的收益点。
- **池自然换血**：号用完 → 出池 → 补冷的进来。

### 6.6 除了池，还有三处性能

| 地方 | 现在 | 建议 |
|---|---|---|
| 每请求三遍全表 | 2.6MB/请求 @1000 号 | 池化后全表读没了（剩一份池名单的拷贝） |
| 会话绑定 | 每次 1 次 SELECT | 内存 LRU 缓存（几百个会话 × 150B），写仍然写库 |
| 卡片的全量快照 | 2.2MB/请求 @1000 号 | 这个规模可以先不动；拆两段读（余额只读 remaining、窗口只读上卡的那几个）是给将来上 10 万号留的门 |

### 6.7 配置建议（200–1000 号）

| 配置 | 现在 | 建议 | 为什么 |
|---|---|---|---|
| `concurrency.per_account` | 1 | 1（不动） | 每号同时一个请求 |
| 总并发 | 可用号/5（至少 3） | 不动，但**要按池夹一下** | 承诺不能超过池 |
| `concurrency.total_max` | 无 | **新增**：0 = 不限；定一个数 = 承诺的上限 | 池空的那一下承诺从库里数，能从 20 抬到 200 —— 天花板是运营的那根杆（§6.9） |
| 池 | 无 | max(总并发, 活跃会话) × 2 | 装得下并发和会话（会话掉了会改绑），再留一倍给补号 |
| 池的内存预算 | 无 | 32MB（= 8.5 万个号，兜底） | 实际用不到 1MB |
| `usage.refresh.scan_every` | 30s | 30s（不动） | |
| `usage.refresh.batch` | 6 | 池大时调到 10–20（并发仍是 4） | 12 个/分钟读不完一个大池 |
| `usage.refresh.card` | 2 | 2（不动） | 卡片现读最热的两个 |
| `usage.refresh.hot_window` | 5m | 5m（不动） | |

### 6.8 「活跃会话」怎么算：网关把用过的会话写回去

**问题**：`sessions.updated_at` 原来只在**改绑**的时候刷新。一段一直用同一个号的对话从来不改绑，它的 `updated_at` 就停在当初绑定的那一刻 —— 一小时之后看起来就不活跃了。而它明明一直在用。

**后果**：池子公式里的「活跃会话数」这一项永远是 0（除非刚改绑过），池实际只按并发算；而且重启后池子按「最冷的号」重填，被绑定的号都是热的、填不进去 → **每段在跑的对话第一次请求就改绑，上下文缓存丢一次**。

**怎么办**：网关知道「这段对话用过没有」—— 上游不告诉它，是它自己知道的。所以：

- **每次请求真的用了这个会话，网关就把它的 `updated_at` 刷新一下**。刷新是**攒着写**的：一批一次（20 秒一趟），不是每个请求写一行 —— 一行 SQLite 写不算什么，但它会跟读额度抢写锁，而读额度是要紧的活。
- **「活跃」的窗口是 1 小时**（`pool.session_window`）：这段时间里被碰过的会话算活跃。
- **填池时，最近活跃的对话绑着的号排最前**。池的大小 = max(总并发, 活跃会话数) × 2 ≥ 2 × 活跃会话数，所以这些号装得下。

**为什么是写库而不是记在内存里**：内存里的账一重启就没了 —— 而「重启后池子认得这些对话」正是要解决的问题。写回去，重启之后头几趟请求就把它补回来。

**代价**：每 20 秒一次小写入（`UPDATE sessions SET updated_at = ? WHERE session_key IN (…)`）。一批一次，不抢读额度的写锁。

### 6.9 并发怎么控：三道闸 + 一个顺序

**要控的是哪一个量**：同时在飞的请求数。号从来不是瓶颈（池子里几百个号），**上游的额度和上游的耐心才是**。所以「并发可控」=「同时打给上游的请求数是可控的」。

**池子一下子空了怎么办** —— 那是最坏的一种失控：池空了，承诺的并发跟着掉（第一道闸），但兜底会从库里数，承诺又抬回去，而且兜底没有池子那么凉（几十个号在库里，够打），于是变成一片 429。所以这一版要按住的是**承诺**，不是号。

**用量摊在不同的号上**：一个号被反复烧光，跟所有号一起慢慢烧，是两种完全不同的失败。前者要一路换号、撞空要一个上游请求、还占着并发；后者只是每个号都少一点。挑号的规矩（下面那五条）就是管这个的。

**第一道闸：池夹**（不变量 4）。承诺的并发不超过池里能用的号数 —— 池里 40 个号就只承诺 40。

**第二道闸：天花板**（`concurrency.total_max`）。池空的时候承诺是从库里数出来的：库里 1000 个号就承诺 200。那一下能从池子撑的数抬到库里的数，而池子还没填上的那一段正好撞上它 —— 那是最容易失控的一下。天花板把它按住：定 64 就永远不超过 64。

天花板是**运营的那根杆**：池子的大小是按承诺的并发算的（max(总并发, 活跃会话数) × 倍数），天花板定 64，池子就是 128 个号 —— 「n×2」那个说法才有着落。0 = 不限（跟从前一样）。

**第三道闸：每个号一个**（`concurrency.per_account` = 1，不动）。

**池空的时候要能干活，但兜底不能是三个全表读**。池空的时候适配器回到从前的样子从库里拿账号、耗尽标记、余额 —— 那三样都是全表读（1000 个号 2.6MB），一个请求一次就是一次。几十个并发就是一波几百 MB。**兜底的结果缓存一秒**：那一波只读一次。窗口不能长：长了就 stale —— 刚被标记成「额度用完」的号还看得出能用。

**轮转要真的是轮转**。池里的号按**进池的顺序**排：轮转从队首走到队尾，冷号（先进来的）先被挑。一个号出池再进池，它排到队尾 —— 它刚用过。（map 的顺序是随机的：随机的顺序让轮转不是轮转。）

**选号的规矩，从要紧的到不要紧的**：

1. **读到余额的排前面** —— 那是能拿来比较的数字。没读到的不算零（不变量 2）。
2. **读到「0」的排到有数的号后面** —— 它接不了活了，挑它就是撞一次空；撞空要一个上游请求，还占着并发。
3. **最久没用过的排前面** —— 余额在这里只当门槛（是不是 0），不当排序的依据。用量摊开：别让一个号被别的号挤在后面一直闲着，到头来被一口气烧光（§6.5）。
4. 一样的话余额多的排前面。
5. 再一样就按 ID 排 —— 稳定：同样的情况挑出同一个号来。

（从前是「余额多的排前面，余额一样才看用没用过」。那不是「先烧哪个」的问题 —— 那是把最富的号先烧光，池子从一头空过去。这一版反过来：用得最少的先上。）

## 7. 四条不变量

1. **池只是缓存，不是真相。** 账号、耗尽标记、会话绑定的真相都在库里。池丢了，重启后从库里重建就行；池里的数过期了，读额度补上。**任何时候池都不能是「唯一知道账号存在的地方」。**
2. **没读到的不是零。** 池里一个号的积分没读过，就是「没读到」，不是 0。它在选号时排在有数的号后面（跟现在一样）。
3. **会话黏性只有「额度用完」能破。** 忙不是理由，请求内换号也不改绑（现在就是这样）。会话钉的号出池了 → 改绑（历史照带）。**所以池子要留着对话绑着的号** —— 池子装不下它，改绑就是缓存命中没了。
4. **承诺的并发不超过池。** 池装不下就少承诺，不能一边说能接 200 一边只有 40 个号。

## 8. 范围

### 8.1 这次要做

- 内存里的账号池（有上界），选号、剩余积分都从池里读。耗尽标记的真相在库里 ——
  额度用完的号当场出池，池里没有用完的号。
- 池的填充（启动时用库里的数顶上）与补号（额度用完 → 补冷的进来）。
- 补号时读一次额度（读不到或读出「用完」就不进池）。
- 总并发按池夹。
- 配置：倍数、池上限、内存预算。
- **把用过的会话写回库**（攒着写，一批一次）：「活跃会话数」要有个真的数（§6.8）。
- **填池时先装最近活跃的对话绑着的号**：会话钉的号不在池里就会被改绑，缓存命中就没了（§6.8）。

### 8.2 这次不做

| 不做 | 为什么 |
|---|---|
| 会话绑定的内存缓存 | 现在每次请求一次索引查询（`sessions` 表主键），几十微秒；池化之后每请求本来就只剩这一次数库，省它的收益小、失效面大 |
| 卡片那条路拆两段读 | 200–1000 个号时它只占 2MB；上到 10 万号才是生死线（另开一份规格） |
| 池里的号按「一阵子没用」换出 | 换出要重读额度，贵；而且会把会话钉的号换掉，缓存命中率掉。**只按额度用完出池** |
| 池里的计划窗口（`windows_json`） | 选号用不上；放进去内存账从 395B 变 2168B |
| 一个号同时跑多个请求 | `concurrency.per_account` 已经是 1，不动 |
| **读额度的令牌桶** | 现在读额度的开销是 `usage.refresh` 的 4 并发 + 6 个/30s，已经有上界。池子跑起来、看到真实的耗尽形态之前，先不动它 —— 参数要拿真的数据来定（另开一份规格） |
| **每个窗口组一个熔断器** | 一个组的额度用完了，那个组该不该停手，现在靠「标记用完 → 出池」就够了。组级别的开关要有真的耗尽数据才说得清（另开一份规格） |
| **失败的号短冷却** | 现在失败的号只是这一趟换下一个（重试上限 3）。要不要给它一段冷却，要看失败是「额度没了」还是「网络抖」—— 那是两种病，不能一起治（另开一份规格） |
| **把池里读到的余额写回去**（`pool.SetRemaining`） | 定时读额度的那趟在 `internal/scheduler` / `internal/manager` 里，它们手里没有池。接起来要改那两处的结构 —— 跟「池归谁管」一起做，别夹在中间（另开一份规格） |

## 9. 好处（为什么值得做）

- 选号的开销跟总账号数脱钩：账号从 100 涨到 10000，挑号的代价不变。
- 内存有上界：池是 max(总并发, 活跃会话数) × 2 个号，不随库里的号数涨。
- 额度实时性的代价可控：**只有快被用到的号需要准的数**（进池读一次、刚用过读一次），读额度的开销跟池大小成正比，不跟总账号数成正比。
- 会话黏性 + 缓存命中：同一段对话始终同一个号，上下文缓存命中率高。

## 10. 要小心的地方

- **n\*n 是白做的**（§6.3）：号少的时候 n\*n 会把号全装进池（等于现在的整表读），号多的时候 n\*n 远大于并发需要。倍数定 2，池按「装得下并发和会话」来。
- **补冷号要读额度**：并发峰值时补得勤，这笔上游开销要算进去（读一次 = 2~11 个上游请求）。补号是后台的，不挡请求。
- **池里的号会变热/变冷**：出池的标准是「额度用完」，不是「一阵子没用」。这两个标准混起来会把池清空。冷号在池里就一直占着位置 —— 所以后台那轮读要覆盖「池里被用过的」，而不是「池里最热的几个」。
- **对外承诺的并发不能按库里的号算**：池没填满却按库里承诺并发 = 一片 429（§6.3）。
- **会话表没有过期**（`sessions` 行从来不删，`store.go:2132`）：池换号改绑是覆盖写，不涨行；但老的绑定还是会留在库里。
- **并发口径**：`concurrency.per_account` 默认 1（`internal/config/config.go:275`），总并发是「可用账号数的 1/5，至少 3」（`internal/gateway/busy.go:148-168`）。池要照着这个口径算，别自己发明。

## 11. 怎么验

- 单元测试（`internal/pool`）：进池、出池、满了不收、标记用完、剩余积分的读写、补号（读到有额度就收、读到用完就标记并换下一个）、**号按进池的顺序排**（出池再进来排到队尾）、**池被读被写的时候是安全的**。
- 单元测试（`internal/store`）：候选账号的查询 —— 排除池里的、排除用完的、没读过的排前面、读过的按最久没读排前面。
- 单元测试（`internal/gateway`）：挑号不再读全表（用一个会数行数的假 store）、耗尽之后池里少一个并且补进来一个、总并发按池夹、**总并发不超过天花板**、**池空的时候库只读一次**（一秒的窗口）。
