# 上游回包的大小：32 MiB 是多少 token，那个数该在哪儿 —— 设计

日期：2026-11-21
状态：待定。
计划：`docs/superpowers/plans/2026-11-21-mmxcode-upstream-body-limit.md`。

## 1. 原话

用户问：「上游回包 32MIB 对应大模型的 token 是多少？」

问完了以后我说的是：

> 32 MiB 大约是 800 万到 1200 万 token。对照模型自己的天花板（接口真的收
> 1,048,576 个输入 token 和 524,288 个输出 token），一次回答最多 1.6–2.1 MB
> —— **32 MiB 是那个真实上限的 13–20 倍**。
>
> 顺带一个更要紧的发现：`maxBody = 32 << 20` 只在 `upstream.ReadBody` 里生效，
> 而**聊天的回答这条路根本没有限额**（`internal/gateway/gateway.go:983` 是裸的
> `io.ReadAll`）。请求那边倒是有闸（32 MiB），回包那边没有。
>
> 要不要我把这两件事一起做掉：
>
> 1. 给聊天的非流式回包加一道限额（超了报错而不是截断）；
> 2. 把 32 MiB 做成可配 —— 按实测的真实天花板（2.5 MB），**8 MiB 就够了**
>    （3 倍余量），比 32 MiB 省四分之三的每请求内存。

用户答：「可以」。

## 2. 32 MiB 是多少 token

32 MiB = 33,554,432 字节。token 和字节的换算看文字是什么：

| 文字 | 每个 token 几个字节 | 32 MiB ≈ |
|---|---|---|
| 中文（UTF-8，3 字节/字，≈1 token/字） | ~3 | ~1100 万 token |
| 英文散文（≈4 字符/token） | ~4 | ~840 万 token |
| 代码/JSON（转义把 `\n` 变成两个字节） | ~2.5–3 | ~1100–1300 万 token |

**所以：800 万到 1200 万 token。**

对照站点自己收的数（`internal/site/models.go:110`，实测出来的）：

| 量 | token | 折成字节 |
|---|---|---|
| 一次回答的上限（输出） | 524,288 | 1.6–2.1 MB（加上 JSON 转义，2.5 MB 封顶） |
| 一次请求的上限（输入） | 1,048,576 | 3.1–4.2 MB |

**32 MiB 是那个真实上限的 13–20 倍。**也就是说：这个限额**永远不会被一个正经
回答碰到** —— 真碰到了，说明上游发的根本不是回答（一个不收尾的流、一张永远发
不完的错误页）。它是个兜底，不是配额。

## 3. 找到的洞

### 洞一：聊天的回答没有限额

`internal/upstream/client.go:105` 那个 `maxBody = 32 << 20` 只在
`upstream.ReadBody` 里生效。`ReadBody` 服务的是**读额度、模型名单、签到、续签**
这些小回包。

**聊天的回答不走它**：`internal/gateway/gateway.go` 的 `attempt` 里是裸的
`io.ReadAll(resp.Body)` —— 上游发多少，进程就吃多少。三处都是：

- `gateway.go:978` —— 上游不是 200（错误页）：整个读进来。
- `gateway.go:983` —— 不是流式的回答：整个读进来。**这是平常走的那条路**。
- `gateway.go:994` —— 200 但身体里是错误（流式的错误）：整个读进来。

流式那条路没事（`io.Copy` 逐块转给客户端，内存是有界的）。

### 洞二：小回包那个 32 MiB 是纯浪费

读额度、模型名单、签到、续签的答都是几个 KB 的 JSON。32 MiB 的闸对它们来说是
一千倍的余量 —— 而闸开着就意味着**每个在飞的请求最多占 32 MiB**。

### 洞三：那个数是写死的

`maxBody` 是一个常量。站点改了它自己的上限，我们改不了；我们要放宽，也只能改
代码重新编。

## 4. 改什么

### 4.1 配置里加一个键

```yaml
upstream:
  timeout: 120s
  site: global
  max_body_mb: 8
```

**默认 8 MiB**：站点的两个天花板折成字节是 1.6 MB（输出）和 4.2 MB（输入），
加上 JSON 转义也不到 5 MB —— 8 MiB 是它上面的一个整数。

**不许写 0 或负数**（`checkUpstream` 报错）：0 会被读成「没有上限」，那正是要
修的那个洞。

### 4.2 那个数只有一个地方知道

`internal/upstream` 里有一个进程范围的数：

```go
const DefaultMaxBody int64 = 8 << 20
var maxBody atomic.Int64
func SetMaxBody(n int64)
func MaxBody() int64
```

**为什么不是一个字段挂在谁身上**：回包的大小是**上游**的事，不是某个调用方的事
—— 读额度、模型名单、签到、续签、聊天回答，读的都是同一个上游。挂在客户端上
就得把它一路传下去（`account.Sender` 那个接口、`oauth` 的续签器、
`manager.accFor` 另造的那个客户端……），传一遍就多一处能漏的地方。

**为什么不是一个普通的全局变量**：它是开机定一次、之后只读的东西 —— 用
`atomic.Int64` 存，读的时候不会跟写的时候撞。

**谁定它**：`cmd/mmxcode/root.go` 读完配置之后定一次（所有命令都定，所以命令行
的工具和网关是一个数）。

### 4.3 聊天那条路读回包要过闸

`attempt` 里那三处 `io.ReadAll` 都换成过闸的读：

- 读法是一样的：**读满上限就报错，不是截断**。截断的回答是半个回答，客户端
  拿着它当完整的用，比报错糟得多。
- 超过上限是 `*upstream.TooLargeError` —— 网关认得它，**当场答 502，不重试**：
  再问一次同一个账号也是这么大的回答（回答的大小是模型和请求的事，不是账号的
  事），白等一次退避没有意义。
- 上游**不是 200**（错误页）而那个错误页大得读不下时：那个身体被丢掉，客户端
  拿到的是上游的状态码 —— 那个错误页本来也不是给人看的东西。

### 4.4 小回包也走同一个数

`upstream.ReadBody` 用的是那个进程范围的数（4.2），所以读额度、模型名单、签到、
续签的闸从 32 MiB 变成 8 MiB。

### 4.5 写错的值要报错

`upstream.max_body_mb` 写 0 或者负数 → 网关拒绝启动（`checkUpstream`），跟
`sqlite.synchronous`、`schedule.checkin_at` 那些一样。

## 5. 不做什么

| 不做 | 为什么 |
|---|---|
| 给流式的回答加总长上限 | 流没有「总长」：一个长答案本来就可能是几十 MB。流式那条路内存是有界的（逐块转），不用管 |
| 截断超限的回答 | 半个回答比没有回答更糟（客户端会拿它当完整的用） |
| 把上限做成「字节」而不是「MB」 | 仓库里已经有 `cache_mb`、`memory_budget_mb` 这样的键（`cache_mb` 其实是 MiB），跟着走 |
| 改请求那边那道闸（`maxBodyBytes = 32 MiB`） | 请求的上限是站点的输入上限（1,048,576 token ≈ 4.2 MB），32 MiB 也偏大 —— 但那是另一件事，这次不动它 |
| 给上限做「0 = 不限」 | 「不限」正是要修的那个洞，不给它留门 |

## 6. 行为变了的地方

1. **上游回包超过 8 MiB 的请求答 502**（从前：整个读进来，或者在小回包那条路上
   等 32 MiB 才报错）。
2. **小回包（读额度、模型名单、签到、续签）的闸从 32 MiB 变成 8 MiB**。
3. **那个数可以配了**（`upstream.max_body_mb`），配 0 或负数会拒绝启动。

## 7. 怎么量

- **超限的回答被挡住**：让假上游答一个比上限大的身体 → 客户端拿到 502，消息说
  清楚「比多少字节大」。
- **超限不是截断**：客户端拿到的不是半个回答（502 就是一个错误，不是一个答案）。
- **超限不重试**：假上游被问了几次？（一次 —— 同一个账号再问一次也是这么大。）
- **那个数是配置说了算**：配 `max_body_mb: 1` 的话，一兆以上的回答就被挡了。
- **写错的值会报错**：配 0 → 启动时拒绝，消息说清楚。

## 8. 风险

| 风险 | 怎么办 |
|---|---|
| 上限配小了，正经回答被挡住 | 8 MiB 是站点自己那个上限的三倍多；真被挡了，日志里说得清楚（超了多少），调大就是 |
| 那个数是全局的，一个测试改了别的测试也看得见 | 读的时候用 atomic；测试改完要改回去（`t.Cleanup`） |
| 流式的回答还是能占很多内存吗 | 不能：流式那条路是逐块转的，内存是缓冲的大小，不是回答的大小 |
